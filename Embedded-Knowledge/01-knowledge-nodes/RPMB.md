# RPMB

一句话：RPMB 是 eMMC/UFS 里的一个受保护小分区，用密钥、单调写计数器、nonce 和 MAC 做硬件级防重放。

> 注：常被写成 PRMB，标准缩写是 RPMB（Replay Protected Memory Block）。

## 为什么存在

普通 flash 只存比特，没有「这是第几次写」的概念。攻击者可以改数据、把整个分区恢复成旧镜像、在总线上重放旧的写命令或读响应；设备读到的比特是合法的，CRC 也是对的，无法分辨新旧。

RPMB 要解决的就是：在没有「时间」的存储里，造一个攻击者倒不回去的「第几次」，再把这个次数认证起来。

## 三件套

1. 一把 256 位密钥：出厂时一次性写入，之后读不出来；主机侧通常由 TEE/安全世界持有同一把钥匙。
2. 一个 32 位单调写计数器：存在器件里，只增不减，掉电不丢。
3. 一个 MAC 引擎：HMAC-SHA-256。

数据本身不加密。RPMB 保证的是「没被改、不是旧的、确实写到了这个地址」，不是「别人看不到」。

## 写：设备是验证方

```
主机                              设备
 |  读写计数器 ------------------> |
 |  <---- 计数器, MAC ------------ |
 |  认证写(数据, 地址, 块数,
 |          计数器, MAC) --------> |  检查计数器是否等于当前值
 |                                 |  检查 MAC
 |  <---- 结果, 新计数器, MAC ---- |
```

主机写之前必须先知道设备当前的写计数器，并把它算进 MAC。设备检查计数器是不是当前值、MAC 对不对；通过才写入，然后把计数器加一。

挡住三类攻击：

- 重放旧写命令：旧帧里的计数器是旧值，设备当前计数器已经更大，拒绝。
- 改数据：MAC 覆盖数据，改了就失败。
- 把 A 地址的数据挪到 B 地址：MAC 覆盖地址和块数，挪了也失败。

为什么不能把计数器改大？MAC 覆盖计数器，改了过不了。为什么不能自己造一条新写命令？没有密钥，算不出 MAC。

## 读：主机是验证方

```
主机                              设备
 |  认证读(地址, 块数, nonce) ---> |
 |  <-- 数据, 计数器, nonce, MAC - |
 |  检查 nonce 是不是自己刚发的    |
 |  检查 MAC                       |
```

读的时候，主机先生成随机 nonce，设备把数据、当前计数器、nonce 一起算进 MAC 返回。主机验证 MAC，并确认 nonce 是自己刚发的。这挡住「重放旧的读响应」：旧响应里的 nonce 对不上。

注意角色和写相反：写的时候设备验证，读的时候主机验证。所以新鲜度的来源也不同——写靠设备里的计数器，读靠主机刚生成的 nonce。谁判定，谁持有参照物。

## 「硬件级」要加一个限定

- 计数器在存储控制器里，普通 OS 不能直接改；MAC 校验由器件执行。这部分是硬件强制的。
- 密钥和主机侧的 MAC 计算通常在 TEE/安全世界里。密钥放在普通 Linux 里，恶意软件可以偷走，RPMB 就失效了。
- 它防的是通过正常命令接口的重放和篡改，不防拆芯片、探针、故障注入这类物理攻击。RPMB 不是安全元件。
- 整颗芯片恢复旧镜像属于物理攻击。如果旧镜像里的写计数器也一起回去了，单靠 RPMB 不一定能发现；高保证方案会让主机在 TEE/OTP 里再存一个期望值，或依赖器件的防拆和绑定能力。

## 能防什么，不能防什么

| 攻击 | 是否防住 | 靠什么 |
|---|---|---|
| 改 RPMB 数据 | 防 | MAC |
| 重放旧写命令 | 防 | 写计数器 |
| 重放旧读响应 | 防 | 主机 nonce |
| 把数据从 A 地址挪到 B | 防 | 地址、块数进 MAC |
| 改块数或请求类型 | 防 | 这些字段进 MAC |
| 总线上窃听 | 不防 | 数据不加密 |
| 密钥泄露后伪造 | 不防 | 根信任被破 |
| 整颗芯片恢复旧镜像 | 不一定 | 计数器可能一起回滚，需主机独立参照 |
| 换一颗 eMMC | 通常能发现 | 密钥不同，认证失败 |
| 业务层重复提交 | 不防 | 需要业务幂等或序号 |

## 场景

- Android Verified Boot 的 rollback index：支持 RPMB 的设备把回滚索引存在 RPMB，启动时和 vbmeta 里的最低版本比较。
- TEE 的安全存储：OP-TEE 这类实现常把加密后的安全文件系统放在普通存储，把完整性和防重放元数据放在 RPMB。
- DRM、支付、许可证：存计数器、密钥句柄、使用次数。
- 车规、工业：防固件降级、使用计数、篡改状态。

## 工程坑

- 容量小：只放元数据和小状态，别当普通文件系统。
- 写寿命：每次成功写都加计数器并写 flash；高频写会磨损。要合并写、减少写，但注意掉电时别丢最新状态。
- 掉电原子性：写要么成功要么失败，计数器不能回退；要验证器件在异常掉电下的行为。
- 并发：多个 OS/TEE 同时访问要串行化，否则计数器竞争。
- 密钥 provisioning：一机一钥，丢了可能报废，泄露了全盘失效；量产流程要设计好。
- 32 位计数器回绕：理论上会回绕，实际很难碰到；设计上仍要避免高频写。
- 不是所有器件都实现正确：要做重放、回滚、掉电、密钥不匹配的专项测试。
- 数据不加密：敏感内容先加密再写。
