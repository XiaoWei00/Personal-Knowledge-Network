# TLS

一句话：TLS 在不可信信道上建立一条带认证的加密管道，记录层用隐式序号和 AEAD 让重放的旧记录解不开。

## 为什么存在

网络会被偷看、被改动、被重放。TLS 要同时给出四件事：机密性（看不懂）、完整性（改不了）、认证（知道是谁）、新鲜性（不是旧的）。前三个常被混为一谈，第四个才是防重放的核心。

## 只加密、只加校验值，都不够

- 只加密：复制密文再发一次，接收方解密后得到同样的明文，会执行两次。
- 只加校验值：重放的记录内容没变，校验值仍然正确。完整性不等于新鲜性。

接收方必须有一个消息之外的参照物。TLS 的参照物是：这条连接、这个方向、这把密钥下，我期待的第几条记录。

## 隐式序号

TLS 为每条连接、每个方向各维护一个 64 位计数器，从 0 开始，每发/收一条记录加一。序号不放进网络。

不传输的好处：省带宽；攻击者没有可篡改的字段。能同步的前提：TLS 跑在 TCP 上，TCP 保证有序、可靠、去重；TLS 只看到「第 0 条、第 1 条……」。如果底层是 UDP，就必须像 DTLS 那样显式带序号和重放窗口。

这里判断的不是「这条消息以前有没有出现过」，而是「这是不是我期待的下一条」。在有序流里，「旧的」就等于「不是下一条」。

## 序号怎么参与密码学

TLS 1.3 的每条记录：

```
nonce = 静态IV XOR 序号（左填充到 IV 长度）
密文 = AEAD加密(明文, nonce, 记录头)
```

接收方用自己的计数器构造 nonce，解密并验证。序号错，nonce 错，认证标签就对不上；失败直接终止连接，不跳过、不重同步。

记录头（类型、版本、长度）进 AAD，改头也会失败。序号同时保证每条记录的 nonce 不同：即使明文完全一样，密文也不同；nonce 复用对 AEAD 是灾难性的。

TLS 1.2 的做法不同：序号进入 MAC 输入；AEAD 模式下序号进入 AAD，nonce 由显式 nonce 参与构造。效果一样：序号参与认证。

## 最小例子

假设静态 IV 是 12 字节全 0：

- 序号 0 → nonce `00 00 ... 00`
- 序号 1 → nonce `00 00 ... 01`
- 序号 5 → nonce `00 00 ... 05`

发送方发第 0 条，接收方期望 0，解密成功，计数器变 1。攻击者重放第 0 条，接收方期望 1，用 `...01` 解，标签失败。序号不在网络上，改不了；改记录头，AAD 失败；发到另一条连接，密钥不同，也失败。

## 换一条连接为什么也不行

新连接有新的 ClientHello.random、ServerHello.random 和 ECDHE 临时密钥，会话密钥完全不同。旧密文用新密钥解不开；即使重放整条旧握手，服务器生成新随机数，transcript 变了，旧 Finished 也过不了。

顺带得到前向保密：ECDHE 临时私钥用完就丢，长期私钥以后泄露，也解不开过去录下的会话。

## 握手本身的新鲜度与绑定

- 双方随机数必须新鲜，并进入密钥派生；旧随机数导致旧密钥。
- 所有握手消息按顺序做 transcript hash；Finished 用 finished_key 对 transcript hash 做 HMAC。任何替换、插入、重放都会让 hash 变化，Finished 失败。
- CertificateVerify 用服务器长期私钥签 transcript hash，把身份绑到这次握手；旧会话的签名搬不过来。
- 降级保护：服务器支持 1.3 却被压回 1.2 时，会在 ServerHello.random 末尾放 DOWNGRD 标记，客户端看到就中止。
- TLS 1.2 的重协商前缀注入攻击由 RFC 5746 的 renegotiation_info 绑定；TLS 1.3 移除了重协商，只保留 KeyUpdate。

## 0-RTT：TLS 自己承认防不住的地方

会话恢复时，客户端拿上次的 PSK，在第一个 flight 就发加密的应用数据。服务器为了立即解密，必须在握手完成前接受，没有机会发新挑战。所以 0-RTT 天生可重放，也不具备前向保密。

为什么重放能解开：早期数据的密钥只依赖 PSK 和 ClientHello，不依赖新的 ServerHello.random。缓解只能靠服务器侧：单次票据、记录已见的 ClientHello/票据、时间窗口，以及应用层只允许幂等请求使用 0-RTT。

这是 TLS 防重放的边界：它防记录层和握手层，不防应用层语义。

## TLS 1.2 与 1.3 的差别

| 维度 | TLS 1.2 | TLS 1.3 |
|---|---|---|
| 记录保护 | CBC 的 MAC-then-encrypt 或 AEAD | 全部 AEAD |
| 序号位置 | MAC 输入 / AAD | nonce + AAD |
| 握手加密 | 大部分明文 | ServerHello 之后加密 |
| 重协商 | 有，需 RFC 5746 | 移除，只有 KeyUpdate |
| 降级保护 | 无 | DOWNGRD 标记 |
| 0-RTT | 无 | 有，可重放 |

## 顺带说清的安全性质

- 机密性：AEAD；1.3 移除了 CBC、RC4、静态 RSA。
- 完整性：AEAD 标签 + transcript hash。
- 认证：证书链、CertificateVerify、PSK。
- 前向保密：ECDHE。
- 截断：TLS 不保证应用消息完整；`close_notify` 是认证的关闭通知，但攻击者可以直接断 TCP，应用要自己判断消息是否收全。
- 流量分析：记录长度可见；SNI 通常明文；填充和 ECH 是缓解手段。
- 密钥更新：KeyUpdate 后序号重置为 0；AEAD 有使用上限，达到前必须更新。
- 中间人持合法证书、终端被控：TLS 本身解决不了。
